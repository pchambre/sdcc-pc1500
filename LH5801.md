# C for the Sharp PC-1500 (SDCC LH5801 port)

How to write, build and run C programs for the PC-1500 (and the TRS-80 PC-2)
with this fork of SDCC: the memory a program has, how it is called from
BASIC, the calling convention for assembly, and what the library offers.
[README.md](README.md) covers what the fork changes inside SDCC itself.

## Quick start

```c
#include <pc1500.h>

int main(void)
{
    lcdClear();
    lcdPutString("HELLO, PC-1500");
    keyWait();
    return 0;
}
```

```sh
sdcc/support/scripts/build-lh5801.sh hello.c 40C5
```

```
hello-40C5-pc1500.bin
  image: 412 bytes at 0x40C5-0x4260, RAM to 0x428C; CALL &40C5
  reserve it first with NEW &428D (before loading it)
  SD card: HELLO.BIN -- SDLOAD M "HELLO.BIN" loads and starts it
```

On the PC-1500:

1. `NEW &428D` reserves the program's RAM: BASIC's program area then starts
   above it. This clears any BASIC program in memory.
2. Put the image at 40C5H. With the SD-card expansion module,
   `SDLOAD M "HELLO.BIN"` loads it and starts it. Any other way of putting
   the bytes of the `.bin` at the load address works too.
3. `CALL &40C5` runs it (again). The program returns to BASIC when `main()`
   returns or `exit()` is called.

The compiler builds under Linux or WSL (`./configure && make` in `sdcc/`).
[pc1500emu](https://github.com/pchambre/pc1500emu) runs the same `.bin`s on
a PC that has the PC-1500's ROM, which is how the port is tested.

## Output files

`build-lh5801.sh <file.c> [more.c, .rel or .lib ...] [load address]` writes
three files next to where it is run:

| file | what it is |
|---|---|
| `<name>-<addr>-pc1500.bin` | the image, byte for byte as it goes in memory at the load address |
| `<name>-<addr>-pc1500.map` | the linker's map: every symbol's address and each area's size |
| `<NAME>.BIN` | the SD-card file: a 4-byte header (load address, then the address `SDLOAD M` calls, both the load address, big-endian), then the image. The name is the first source's, upper-cased and cut to 8 characters. |

The load address is hex without a prefix. It defaults to 4400, but a program
should go at the bottom of user RAM (below).

The script compiles the runtime library once into a cache, and links only the
modules a program uses. `SDCCFLAGS` passes extra compiler options to every
compile, the library's included (each set of flags gets its own cache).

## Memory

### What a program has

| machine | RAM | load at | room for the program |
|---|---|---|---|
| a PC-1500 as sold | 4000H-47FFH | `40C5` | 1.8K |
| with an 8K RAM card | 4000H-67FFH | `40C5` | 9.8K |
| with RAM expansion to 28K | 0000H-6FFFH | `00C5` | 27.8K |

The first C5H bytes of the RAM BASIC uses are the ROM's (the reserve-key
area). "The program" means everything the build's `NEW` address reserves:
its code and constants, then its variables. The examples show what fits:

| program | code | loads at | `NEW` |
|---|---:|---|---|
| hello world above | 412 B | 40C5 | `&428D` |
| Blackjack (`device/examples/lh5801/blackjack`) | 9568 B | 40C5 | `&6779` |
| LANDER: float physics, `sqrtf`, `sprintf` | 8292 B | 40C5 | `&6383` |
| EDIT: a line editor with a 4K text buffer, `sprintf` | 6808 B | 00C5 | `&2DA1` |

### Layout

From the load address up: the startup code, constants, initial values of
initialized variables, the code (all of this is the `.bin`), then the
variables, which are only RAM. The build prints where the variables end, and
the `NEW` it prints is the address after them.

Every `CALL` starts the program afresh: the startup code zeroes the variables
and copies the initialized ones' values in, so a program can simply be run
again. It keeps BASIC's stack pointer and saves the Y and U registers, which
BASIC needs back.

### Variables at fixed addresses

`__at(addr)` places a variable at an address of your choosing:

```c
__at(0x7650) unsigned char deck[176];
```

The startup code does not zero or initialize these. A program that never
uses BASIC's fixed variables (A-Z, A$-Z$) can keep arrays in their system
RAM at no cost in user RAM: 7650H-76FFH, 774EH-77FFH and 78C0H-79CFH.
Blackjack keeps its decks there. BASIC sees whatever the program left there
as variable values afterwards.

### The stack

A program runs on BASIC's own stack, which is small: the ROM sets S to 784FH,
and the system stack ends at 7800H. Measured in pc1500emu, S is 7842H in
`main()`, both for a `CALL` typed at the prompt and for one in a program
inside GOSUBs and a FOR loop (BASIC keeps those on stacks of its own). That
leaves about **64 bytes** for every call's return address, every reentrant
function's arguments and saved locals, and the ROM's timer interrupt, which
uses the same stack.

Ordinary functions use only 2 bytes of stack per call (the return address),
because their locals and parameters are not on the stack (see below).
Recursion is what uses the stack up: a level of a small reentrant function
such as

```c
static unsigned char down(unsigned char n) __reentrant
{
    return n == 0 ? 0 : down(n - 1) + 1;
}
```

takes 4 bytes (the return address, its argument, and one saved byte), so about
15 levels fit. Nothing checks for overflow. Below 7800H the stack runs into
BASIC's string variables (7750H-77FFH, which `__at` arrays may also be
using), then into display RAM (7700H). Keep recursion shallow, or make it
iteration.

### The heap

`malloc()`, `calloc()`, `realloc()` and `free()` take their memory from a 1K
array that is linked in only when a program uses them, and is part of the RAM
that `NEW` reserves. For another size, define both of these in the program:

```c
char __sdcc_heap[3072];
const unsigned int __sdcc_heap_size = sizeof (__sdcc_heap);
```

The program's own definitions win over the library's. A 3K heap at `40C5`
runs in the 10K layout (checked in pc1500emu: allocation, refusal of a block
too big for what is left, reuse after `free()`).

## Functions

### Locals are static unless a function is reentrant

The LH5801 can't reach a stack frame by an offset, so a function's
parameters and locals are not on the stack. Values of one or two bytes
live in halves of the X, Y and U registers when the register allocator finds
that smaller. Everything else is at a fixed memory address of its own. That
makes calls cheap, but an ordinary function cannot call itself, directly or
through other functions.

For recursion, declare the function `__reentrant`. Its locals are still
static, but on entry it pushes the ones that must survive a call it makes,
and pops them back before it returns, so each level gets its own. Its
arguments come on the stack. A reentrant function costs more code and time
per call than an ordinary one, so use it only where recursion needs it.
`sqrtf()` is reentrant, so it can be called from anywhere.

Functions that are never active at the same time share their locals' memory
(each module's locals are overlaid as a compiled stack). A function that
isn't `static` keeps memory of its own if it calls the library or another
module, since those could call it back, so **declare helpers `static`**
to save RAM.

### Calling through pointers

The LH5801 has no indirect call, so a call through a function pointer goes
through a `JMP` in RAM that the caller patches. That works for any function
whose arguments all go in registers (see the calling convention), and for any
reentrant function. A non-reentrant function with more arguments than that
can't be called through a pointer; SDCC reports error 92 ("Functions called
via pointers must be 'reentrant' to take this many arguments"). Declare it
`__reentrant`.

### Interrupts

`__critical { ... }` blocks run with interrupts off and restore the
interrupt-enable flag afterwards. `atomic_flag` works (on the same masking).
A `__critical` function is not supported (a compile error), and neither is
`__interrupt`: the ROM owns the interrupt vectors.

## Calling convention (for assembly)

Assembly functions go in their own `.asm` files (assembled with
`sdaslh5801`) or inline:

```c
__asm
    ldx  s
__endasm;
```

C names get a leading underscore in assembly (`main` is `_main`). Multi-byte
values are big-endian (byte 0 is the most significant).

**Arguments of an ordinary function:**

- the first 1-byte argument in A;
- the first 2-byte argument in X (XH the high byte);
- every other argument in the callee's own static bytes, `_<func>_PARM_<n>`
  (n counts from 1 in declaration order), written by the caller before the
  call.

```c
int three(char c, int i, long l);   /* c in A, i in X, l in _three_PARM_3 */
```

**Arguments of a reentrant or varargs function** are all on the stack, in
declaration order upwards from S+3 on entry (S+1 and S+2 are the return
address), each big-endian. The caller pushes them and removes them after the
call.

**Return values:**

| size | where |
|---|---|
| 1 byte (`char`, `_Bool`) | A |
| 2 bytes (`int`, pointers) | X (XH the high byte) |
| 3-8 bytes (`long`, `float`) | bytes 0-1 in XH, XL; bytes 2-7 in `__lh5801_ret2` ... `__lh5801_ret7` |
| more | bytes 8-63 in `__lh5801_ret8`..., bytes 64+ in `__lh5801_ret64`... |

**Registers:** a C caller assumes a call to another module or to assembly
clobbers A, X, Y and U. An assembly function needs to keep only S balanced.
(Within one module, the compiler may also keep values in Y and U across calls
to functions it has seen leave them alone.) Programs run from RAM.

## The library

### PC-1500 (`#include <pc1500.h>`)

Thin wrappers around the ROM's own routines; nothing is reimplemented.

| | |
|---|---|
| display | `lcdClear()`, `lcdPutChar(c)`, `lcdPutString(s)`, `lcdSetCursor(cell)` (BASIC's CURSOR, 0-25), `lcdInvert()`, `PC1500_GCU` (the graphic cursor, column 0-155) |
| keyboard | `keyWait()` (sleeps until a key; `PC1500_KEY_BREAK` for BREAK), `keyScan()` (INKEY$: the key down now, or 0), `PC1500_KEY_*` codes |
| line input | `lcdInputLine(buf, max)`: BASIC INPUT-style editing; returns the length, or `PC1500_INPUT_BREAK` |
| sound | `beep()` (BEEP 1), `beepTone(halfPeriod, periods)` |
| time | `delayTicks(n)` (about 360 a second), `idleTick()` (halt until the next timer interrupt), `onKeyPressed()` |
| end | `exit(status)`: back to BASIC from any depth |
| cassette | `tapeSendChar(c)` (needs a CE-150) |
| ROM numbers | `pc1500_float_t`, the ROM's 8-byte BCD format (10 digits), and `pc1500Add/Sub/Mul/Div`, `Sqrt`, `Sin/Cos/Tan`, `Asn/Acs/Atn`, `Log/Ln/Exp`, `Abs/Int/Sgn`, `Deg/Dms`, `pc1500FloatToStr()`, `pc1500Error()` |

`pc1500.h` documents each one, and the `.asm` file behind it (in
`sdcc/device/lib/lh5801/`) gives the ROM address it calls.

### Standard C

SDCC's C library is there, and SDCC's own regression suite passes on the port.
Notes:

- **`printf()`** needs a `putchar()` from the program, as on every SDCC port.
  For the display:
  ```c
  int putchar(int c) { if (c != '\n') lcdPutChar(c); return c; }
  ```
  `sprintf()` into a buffer and `lcdPutString()` needs nothing extra. There is
  no `%f` (as on every SDCC port but ds390); print a float through integers,
  e.g. in tenths. The port has its own smaller `printf` core (1.8K).
- **`float`** is IEEE single precision, by the port's own assembly library
  (1.9K for all of + - * /, the comparisons, the conversions and `sqrtf`).
  Results are correctly rounded (to nearest, ties to even). There are no
  subnormals: a result too small becomes zero. Too large becomes infinity;
  0/0 is NaN; x/0 is an infinity with x's sign. Conversion of a float to an
  integer type that can't hold it saturates. Measured speeds: multiply 4.6 ms,
  add 1.4 ms, divide 9.6 ms. The other `math.h` functions are SDCC's
  portable C versions, built on these.
- The ROM's BCD numbers (`pc1500_float_t`) are a separate type with 10
  digits, for programs that want BASIC's own arithmetic. Each wrapper call
  costs more code than a C float operation.
- `setjmp()`/`longjmp()` work.

## Fitting a program in 10K

What Blackjack does to fit, besides what the compiler does on its own:

- `static` on every function that isn't called from another module (more
  of their locals share memory);
- the largest arrays at fixed addresses in the system RAM BASIC's fixed
  variables would use (above);
- integers rather than `float` where they will do, and `sprintf()` only if
  it earns its 1.8K.

The `.map` file gives each module's size. For the smallest code leave
`--opt-code-speed` off: it inlines what is otherwise in small shared helpers
and turns off the merging of repeated code.

## Compiler options

| option | effect |
|---|---|
| `--opt-code-speed` | inline code instead of the 32-bit and frame helpers; no merging of repeated instruction sequences |
| `--oldralloc` | no register allocation: every value in memory (the original backend; a fallback) |
| `--lh5801-no-overlay` | each function keeps its locals' memory to itself |
| `--lh5801-no-outline` | no merging of repeated instruction sequences into shared subroutines |

## Known limits

- No `__sfr` or other I/O-space (ME1) access from C: use an assembly function.
- No `__interrupt` handlers, and no `__critical` functions (blocks work).
- A non-reentrant function with stack-passed arguments can't be called
  through a pointer (error 92, above).
- No stack overflow check; about 64 bytes of stack (above).
- In SDCC itself, on every port: `void *` arithmetic (`p + 1` on a
  `void *`) compiles as `p + 0`, with no warning. Cast to `char *` first.
